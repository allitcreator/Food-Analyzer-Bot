# Быстрая запись с iPhone (иконка / шорткат)

Исследование, 2026-08-18. Задача: «придумать как шорткатом в brobotfood записывать что-то» —
максимально дешёвый способ закинуть еду в дневник с телефона: от текста до фото, иконкой
на домашнем экране. Код не менялся, ничего не деплоилось — это разбор и контракт.

Прямо ложится на релиз 1 дорожной карты («убить рутину ввода»): самое частотное действие
должно стать самым дешёвым.

---

## 1. Что бот умеет записывать сейчас и какими путями

**Единственная точка входа для новых данных — сообщение боту в Telegram** (`server/bot.ts:3419`,
хендлер `bot.on("message")`). Три формата:

| Вход | Цепочка |
|---|---|
| Текст | `classifyIntent` → еда / тренировка / оба → `analyzeFoodText` (gpt-4o-mini) → карточка подтверждения |
| Фото | zxing-декод штрихкода → кэш `barcode_products` → Open Food Facts → иначе vision gpt-4o → карточка |
| Голосовое | Gemini 2.0 Flash транскрибация → дальше как текст |

Дальше — карточка подтверждения с инлайн-кнопками: править вес/калории/БЖУ (пропорциональный
пересчёт), сохранить, отменить. Мультиблюдо разбирается по позициям. `mealType` ставится по
времени пользователя. Вода отделяется от еды флагом `hydrating`.

Вес — только командой `/weight 78.4`. Вода — из Mini App или через `hydrating`-позиции.

**Второй путь — Mini App** (`server/app-api.ts`, монтируется на `/api/app`): `POST /analyze`
(текст или `imageBase64`) + `POST /logs` (записать подтверждённые позиции). Штрихкоды тут
НЕ работают — эта ветка живёт только в `bot.ts`.

Авторизация Mini App: заголовок `Authorization: tma <initData>`, подпись HMAC-SHA256 по токену
бота, `auth_date` не старше **86400 с** (`server/lib/telegram-auth.ts:50`). Это ключевое
ограничение для всей задачи — см. §3.

Деплой: VPS, docker compose (bot + postgres), nginx перед контейнером, webhook на
`https://<домен>/api/telegram-webhook/<WEBHOOK_SECRET>` с проверкой заголовка
`X-Telegram-Bot-Api-Secret-Token` (`server/bot.ts:292`).

**Прецедент, который важен.** До коммита `fd09279` в проекте уже жил ровно такой шорткат:
Apple Health слал данные на `POST /api/health-sync/:token`, токен генерился командой `/sync`,
хранился в `users.health_sync_token` (unique), сбрасывался кнопкой. Интеграцию снесли не
потому, что схема плохая, а потому что пользователь ушёл на Whoop. Аудит тогда поймал один
дефект схемы: **токен в URL утекал в nginx access-логи**. Это учтено ниже.

## 2. Варианты быстрой записи с iPhone — честно, с ограничениями

Факты по iOS проверены на актуальной версии (публичная — **iOS 26.6.1**, iOS 27 в бете;
всё, что появилось в iOS 18, в 26 уже есть).

### 2.1. Шорткат → собственный HTTPS-эндпоинт

Действие «Получить содержимое URL» (Get Contents of URL) умеет:
- методы GET/POST/PUT/PATCH/DELETE;
- тело запроса JSON / Form / File (только для POST/PUT/PATCH);
- **произвольные заголовки, включая `Authorization`** — это и есть решение задачи авторизации;
- multipart с файлом — через тип тела Form с файлом в значении поля.

Ограничения, которые придётся заложить в контракт:
- встроенный редактор JSON умеет **только плоский словарь** ключ→значение. Вложенные объекты
  и массивы собираются грязным трюком (Text-действие → тип тела File). **Значит тело нашего
  эндпоинта должно быть плоским.**
- Shortcuts сам выставляет `Content-Type` по типу тела и игнорирует ручной заголовок.
- HTTPS обязателен, самоподписанный сертификат ронит запрос без внятной ошибки.

Фото: «Сделать фото» / «Выбрать фото» → «Изменить размер» → «Конвертировать в JPEG» →
«Кодировать в Base64» (обязательно `Разрывы строк: Нет`, иначе LF ломает строку). Base64
раздувает данные на ~33 %; жёсткого документированного лимита у Apple нет, упирается в память
расширения. Альтернатива — multipart без base64, но её сервер сейчас не умеет (нет multer).

### 2.2. Иконка на домашнем экране

Официально: шорткат → Details → «Добавить на экран “Домой”», можно своя иконка и имя.
Технически это Safari web clip. **С iOS 14.3 тап больше не открывает приложение «Команды»** —
headless-шорткат просто выполняется, интерактивный показывает компактную карточку сверху.

Что нельзя: убрать баннер «шорткат запущен», который всплывает при каждом запуске. Штатной
опции нет, Apple её так и не сделала. Живём с ним.

### 2.3. Запуск в один тап: Пункт управления / локскрин / Action Button / Back Tap

Всё это официально поддержано: контрол Shortcut в Пункте управления (iOS 18+), замена двух
контролов на локскрине, Back Tap (двойное/тройное касание задней крышки), Action Button на
15 Pro и новее.

**Общее ограничение, которое убивает половину мечты**: если шорткат требует ввода или
открывает приложение, iPhone потребует разблокировки. Молча с локскрина отрабатывает только
полностью headless-шорткат. А «Запросить ввод», «Диктовать текст» и «Сделать фото» — все
интерактивные. То есть Action Button и Пункт управления дают не «без Face ID», а всего лишь
«не искать иконку глазами». Разница с иконкой на домашнем экране — почти нулевая.

### 2.4. Share Sheet

Официально: Details → «Показывать в меню “Поделиться”», в начале шортката появляется действие
«Получить» (Receive) с выбором типов. Для фото из галереи — оставить только Images.
Гоча: шорткат с типом Images всплывает и при шаринге веб-страницы из Safari.

Это лучший путь для «фото уже снято» и для скриншотов этикеток.

### 2.5. Telegram deep links — тупик для записи данных

- `https://t.me/<bot>?start=<payload>`: payload **не длиннее 64 символов**, алфавит только
  `A-Za-z0-9_-` (бинарное — через base64url, то есть ~48 байт сырых данных). Фото — исключено
  в принципе. Плюс открытые баги клиентов: Desktop каждый раз требует тапнуть START, на iOS
  зафиксированы случаи, когда повторный deep link молча не доставляет payload до перезапуска
  приложения.
- `?text=<draft>`: в спецификации Telegram это **черновик** в поле ввода, «if the user can
  write in the chat». Отправляет сообщение всегда человек руками. Пока бот не запущен, поля
  ввода вообще нет — вместо него кнопка START. Выигрыш относительно «просто открыть чат» — ноль.
- Attachment menu (`?startattach`) — доступен только крупным рекламодателям Telegram Ad
  Platform. Для личного бота закрыт.

### 2.6. Telegram Bot API из шортката — не работает по сути

Шорткат может позвать `sendMessage`/`sendPhoto` с токеном бота и своим `chat_id`. Но Bot API
аутентифицирует **бота**, а не пользователя: сообщение придёт **от бота**, и своё собственное
исходящее сообщение бот апдейтом не получит — цепочка анализа не запустится. Писать от имени
пользователя можно только userbot'ом на MTProto (риск для аккаунта) или через Telegram Business
connection (это про ответы бота от имени владельца, а не про ввод). Вариант закрыт.

### 2.7. Что уже работает сегодня без единой строки кода

Фото → «Поделиться» → Telegram → чат с ботом. Работает, ноль разработки, но 4 тапа и поиск
чата в списке. Закреплённый наверху чат с ботом + камера прямо в Telegram — примерно то же.
**Это база для сравнения: любой шорткат обязан быть быстрее этого, иначе он не нужен.**

### 2.8. Ложный путь, который выглядит соблазнительно

«Добавить на экран “Домой”» из Safari для `https://<домен>/app/` — Mini App иконкой. **Не
работает**: вне Telegram нет `window.Telegram.WebApp.initData`, каждый запрос к `/api/app/*`
получит 401 `missing_init_data`. Приложение откроется и будет пустым.

## 3. Главная развилка: чем авторизовать запись из шортката

### Отвергнуто: захардкодить initData в шорткат

Строка валидируется чисто криптографически и формально будет проходить вечно — но наш
`validateInitData` режет её по `auth_date` через **24 часа** (`maxAgeSec = 86400`). Шорткат
умрёт назавтра. Ослабить проверку до бесконечности = сознательно снять защиту от replay:
украденная строка становится вечным пропуском. Плюс `query_id` внутри initData привязан к
сессии мини-аппа и протухает независимо. Официальная рекомендация ровно обратная: валидировать
initData один раз с коротким TTL и выдавать свой session token. Тупик.

### Отвергнуто: ограничение по IP

У телефона динамический IP, LTE, роуминг, Wi-Fi. Неработоспособно.

### Отвергнуто: подпись запроса (HMAC от тела + timestamp)

Шорткат не умеет считать HMAC штатным действием — придётся тащить Data Jar / Scriptable /
JavaScript-обвязку. Стоимость сборки и хрупкость выше, чем выигрыш в безопасности, при том
что защищаем мы дневник питания одного человека.

### Отвергнуто: слать на существующий webhook боевым секретом (кроме как прототипом)

Технически идеально: `POST https://<домен>/api/telegram-webhook/<WEBHOOK_SECRET>` с заголовком
`X-Telegram-Bot-Api-Secret-Token` и телом-подделкой Update — сервер обработает это как обычное
сообщение, **ноль строк нового кода**. Цена: на телефоне лежит `WEBHOOK_SECRET`, а он позволяет
подделать сообщение от **любого** пользователя бота, и это единственная защита вебхука.
Как разовый эксперимент «проверить гипотезу за 10 минут» — годится (см. §6), как постоянная
схема — нет.

### Рекомендуется: отдельный эндпоинт + персональный bearer-токен

`POST /api/quick`, заголовок `Authorization: Bearer <quick_token>`. Токен — колонка
`users.quick_token` (unique), выдаётся командой `/quick`, сбрасывается кнопкой. Прямой аналог
уже жившего в проекте `health_sync_token`, но **токен в заголовке, а не в URL** — прошлый аудит
поймал именно утечку токена в nginx access-логи.

Чем платим:
- на телефоне лежит долгоживущий секрет; шорткаты синкаются в iCloud и экспортируются ссылкой —
  утёкший токен даёт запись мусора в один дневник и, что дороже, **трату OpenRouter на чужие
  AI-вызовы** (один текстовый ввод = 2 вызова: `classifyIntent` + `analyzeFoodText`);
- лечится тремя вещами: жёсткий rate-limit на токен (30/час), мгновенная ротация из бота,
  токен ничего не читает — только пишет.

Альтернатива на вечер, если не хочется миграции: один `QUICK_TOKEN` в `.env` + `ADMIN_TELEGRAM_ID`
как получатель. Три строки кода, но: не ротируется без редеплоя и работает только для одного
человека — а в релизе 4 запланирована семья. Поэтому колонка в БД.

## 4. Рекомендуемый вариант и пользовательский сценарий

### Архитектура

**Один эндпоинт, который не дублирует логику, а скармливает боту синтетический апдейт.**

```
шорткат ──POST /api/quick──▶ проверка Bearer-токена
                              │
                              ├─ текст: injectUserMessage(tgId, text)
                              └─ фото:  bot.sendPhoto(tgId, buffer) → file_id
                                        → injectUserMessage(tgId, photo: file_id)
                              │
                              ▼
                        bot.processUpdate(...)  ← существующий обработчик
                              │
                              ▼
                 карточка подтверждения приходит пушем в Telegram
```

Почему именно так, а не «эндпоинт сам анализирует и пишет в БД»:

1. **Штрихкоды.** Ветка zxing → кэш → Open Food Facts живёт только в `bot.ts:3818` и в
   `/api/app/analyze` её нет. Инъекция апдейта отдаёт её бесплатно — а фото упаковки это
   как раз самый частый быстрый ввод.
2. **Ноль дублирования UI подтверждения.** Карточка, редактирование веса с пропорциональным
   пересчётом, мультиблюдо, распознавание тренировок — это тысячи строк, которые не надо
   переписывать.
3. **Правка кривой оценки AI остаётся возможной.** Молчаливая запись без подтверждения быстрее,
   но AI регулярно промахивается с весом порции, и промах уедет в дневник незамеченным.
4. `bot.sendPhoto` перед инъекцией даёт побочный плюс: фото остаётся в истории чата — видно,
   что именно записывал.

Чем платим: `injectUserMessage` — это наш договор с формой Telegram `Update`, а не публичный
контракт библиотеки. Смена `node-telegram-bot-api` заставит его переписать. Держать одной
маленькой функцией рядом с `setupBot`, покрыть тестом на форму апдейта.

### Один шорткат, две точки входа — не три

- **Иконка на домашнем экране** (плюс тот же шорткат в Пункте управления, если захочется) →
  «Выбрать из меню» с двумя пунктами: `🎤 Сказать или написать` и `📷 Сфотографировать`.
- **Меню “Поделиться”** → тот же шорткат принимает уже готовое фото из «Фото».

Почему не отдельный шорткат под голос: «Запросить ввод» открывает клавиатуру, а у неё есть
кнопка микрофона — то есть текст и диктовка покрываются **одним** действием, и опечатку можно
поправить. Отдельное действие «Диктовать текст» жёстко завязано на офлайн-модель распознавания
(поддержка русского в on-device-режиме официально не подтверждена, проверяется только на самом
устройстве) и не даёт исправить результат.

Почему не три иконки на каждый формат: три копии URL и токена, и любая правка контракта — три
правки в трёх местах. Меню стоит один тап.

### Сценарий по шагам

1. Тап по иконке «Еда» на домашнем экране.
2. Face ID. **Обойти нельзя** — любой ввод/камера требуют разблокировки, это ограничение iOS,
   а не нашей схемы.
3. Меню из двух пунктов — тап.
4. **Голос/текст**: сказал «овсянка на молоке 250 грамм и кофе с молоком» → «Готово».
   **Фото**: камера → снял → «Использовать фото».
5. Шорткат шлёт POST и показывает уведомление «Отправил на разбор». Всё, телефон можно убрать.
6. Через 3–10 секунд приходит пуш от бота: карточка с КБЖУ и кнопками `✅ Сохранить` /
   `✏️ Вес` / `❌ Отмена`. Мультиблюдо — списком по позициям.
7. Тап «Сохранить». Если AI ошибся с весом — правим тут же, как обычно.

Итого: 3 тапа + фраза голосом против «открыть Telegram → найти чат → нажать микрофон →
наговорить → отправить». Экономия честная, но не драматичная — главный выигрыш в том, что
не надо заходить в Telegram и не надо думать, в каком ты чате.

## 5. Технический контракт

### Эндпоинт

```
POST /api/quick
Authorization: Bearer <quick_token>
Content-Type: application/json
```

Тело — **плоский словарь** (ограничение редактора JSON в Shortcuts, см. §2.1), хотя бы одно из:

```json
{ "text": "овсянка на молоке 250 г и кофе с молоком" }
```
```json
{ "imageBase64": "<JPEG в base64, без data:-префикса>" }
```
```json
{ "imageBase64": "<...>", "text": "это борщ, 400 г" }
```

Третий вариант — фото с подписью: `text` становится подписью к снимку в чате и уезжает в
vision как приоритетная подсказка (это и есть починенный P1-баг №10).

Ответ `202 Accepted`, поле `accepted` — что именно приняли (`"text"` / `"photo"` / `"photo+text"`):

```json
{ "ok": true, "accepted": "text" }
```

Ошибки: `401 invalid_token` · `403 blocked` / `not_approved` · `400 validation_error` ·
`413 too_large` · `429 rate_limited` · `500 internal_error`.

Отдаём 202 и не ждём AI: анализ занимает 3–30 секунд, шорткату столько висеть незачем,
результат всё равно придёт пушем в Telegram.

### Валидация

Отдельная `quickSchema` в `shared/routes.ts` (а не `analyzeSchema`: там ровно одно поле из
двух, здесь допустимы оба сразу): `text` — 1..2000 символов; `imageBase64` — до 1 400 000
символов после нормализации, regex `^[A-Za-z0-9+/]+={0,2}$`.

Переносы строк в base64 сервер вычищает сам (`\s+` → пусто) ДО проверки алфавита: действие
«Кодировать в Base64» в Shortcuts по умолчанию рвёт строку на 76 символов, и требовать от
человека лезть в настройки действия — лишний способ уронить сценарий на ровном месте. Лимит
длины применяется дважды — до нормализации (1 500 000, чтобы строка из одних переносов не
доехала до обработки) и после (1 400 000, по фактическим данным).

Лимиты по пути запроса, все три надо держать в голове:
`nginx client_max_body_size` (в `DEPLOY_GUIDE.md` — 20M, но у боевого location это надо
перепроверить: комментарий в `client/src/lib/image.ts` утверждает, что прод режет тело на 1 МБ)
→ `express.json({ limit: "2mb" })` → 1.4 МБ схемы. Отсюда требование к шорткату: ресайз до
1280 px по большей стороне и JPEG среднего качества, как это уже делает Mini App.

### Хранение токена

```sql
-- migrations/0007_*.sql
ALTER TABLE "users" ADD COLUMN IF NOT EXISTS "quick_token" text;
ALTER TABLE "users" ADD CONSTRAINT "users_quick_token_unique" UNIQUE("quick_token");
```

`randomBytes(24).toString("hex")`, ровно как раньше в health-sync. Команда `/quick` печатает
URL, токен и кнопку «🔄 Сбросить токен».

### Rate-limit

30 запросов/час на токен, ключ — id пользователя. Обоснование: не защита от DDoS, а потолок
трат OpenRouter при утечке токена. Router-wide лимит `/api/app` (120/мин) сюда не подходит —
там дешёвые чтения, тут каждый запрос стоит денег.

### Что трогаем в коде (когда дойдут руки)

- `shared/schema.ts` — колонка `quickToken`; миграция 0007.
- `server/storage.ts` — `getUserByQuickToken`, `setQuickToken`.
- `server/bot.ts` — экспорт `injectUserMessage(telegramId, payload)` (модульная переменная
  `botInstance` уже существует на строке 16, но наружу не отдаётся — нужен геттер) + команда
  `/quick` + кнопка сброса токена.

## 6. Рецепт сборки шортката

### Сначала — проверка гипотезы за 10 минут, без единой строки серверного кода

До всякой разработки можно убедиться, что сценарий вообще удобен. Собрать шорткат из одного
действия «Получить содержимое URL»:

- URL: `https://<домен>/api/telegram-webhook/<WEBHOOK_SECRET>`
- Метод: POST
- Заголовок: `X-Telegram-Bot-Api-Secret-Token` = `<WEBHOOK_SECRET>`
- Тело (JSON): плоским словарём не получится — тут нужен вложенный `message`, так что
  собираем текстом через Text-действие и тип тела File:

```json
{"update_id":1,"message":{"message_id":1,"date":1755500000,
"chat":{"id":<ВАШ_TG_ID>,"type":"private"},
"from":{"id":<ВАШ_TG_ID>,"is_bot":false,"first_name":"A"},
"text":"овсянка 250 г"}}
```

Придёт карточка подтверждения — значит схема живая и стоит писать эндпоинт.
**После эксперимента ротировать `WEBHOOK_SECRET`** (`openssl rand -hex 32` + перезапуск,
`setWebHook` вызовется заново на старте): секрет на телефоне позволяет подделать сообщение от
любого пользователя бота. Фото этим способом не проверить — нужен `file_id`, которого у
шортката нет.

### Боевой шорткат (после того, как `/api/quick` появится)

Названия действий даны как в русской локализации, в скобках — оригинал.

1. **Получить** (Receive) — «Изображения» из меню “Поделиться”, «Ничего» при запуске без входа.
2. **Если** (If) вход не задан → идём в меню, иначе сразу к шагу 6 с полученным фото.
3. **Выбрать из меню** (Choose from Menu): `🎤 Сказать или написать` / `📷 Сфотографировать`.
4. Ветка «Сказать или написать»: **Запросить ввод** (Ask for Input), тип «Текст», подсказка
   «Что съел?». Диктовка — кнопкой микрофона на клавиатуре.
5. Ветка «Сфотографировать»: **Сделать фото** (Take Photo), «Показывать превью камеры» — вкл.
6. Для фото: **Изменить размер изображения** (Resize Image) → 1280 по большей стороне →
   **Конвертировать изображение** (Convert Image) → JPEG, качество среднее →
   **Кодировать в Base64** (Base64 Encode). Настройку «Разрывы строк» можно не трогать —
   сервер склеит строку сам (см. §5); выключенные переносы лишь экономят ~1.3% трафика.
7. **Получить содержимое URL** (Get Contents of URL):
   - URL `https://<домен>/api/quick`
   - Метод `POST`
   - Заголовки: `Authorization` = `Bearer <токен из /quick>`
   - Тело запроса: `JSON`, одно поле — `text` или `imageBase64` со значением-переменной.
8. **Показать уведомление** (Show Notification): «Отправил на разбор».
9. Details: **Показывать в меню “Поделиться”** — вкл; **Добавить на экран “Домой”** — иконка
   с названием «Еда».

Опционально: тот же шорткат — контролом в Пункт управления или на Action Button. Помним, что
Face ID это не отменяет (§2.3).

Порог входа: 8 действий, собирается за 15 минут. Если понадобится ставить шорткат ещё кому-то
из семьи — публикуется ссылкой на iCloud (как раньше делали с HealthSync), токен каждый
подставляет свой.

## 7. Решения по открытым вопросам (2026-08-22) — РЕАЛИЗОВАНО

Ответы Александра и что из них вышло в коде:

1. **Подтверждение** — карточка, режим «записал и забыл» не делаем. Эндпоинт вбрасывает
   апдейт в бот, дальше работает штатная карточка с правкой веса.
2. **Домен** — не зашивается: `/quick` печатает адрес из `WEBHOOK_URL`, то есть всегда
   актуальный боевой домен.
3. **Объём** — еда (текст + фото) и вода. Вода уже ехала штатной цепочкой (флаг `hydrating`
   → счётчик воды), поэтому правка одна: в `classifyIntent` убран edge-case
   «выпил воды → other», который отправлял воду в ветку «не понял». Вес через `/weight`
   как был — сознательно не трогали.
4. **Подпись к фото (P1-баг №10)** — починена: `msg.caption` уезжает в vision как `userNote`
   с приоритетом над визуальной оценкой. Работает и в боте, и в быстрой записи.
5. **Токен** — колонка `users.quick_token` (миграция 0007), выдаётся лениво по `/quick`,
   сбрасывается кнопкой.
6. **Шорткат** — собирается руками по рецепту §6; ссылку на iCloud сделаем, если понадобится
   ставить его кому-то ещё.

Реализация: `server/quick-api.ts`, `server/lib/quick-auth.ts`, `server/lib/synthetic-update.ts`,
команда `/quick` и `injectUserMessage` в `server/bot.ts`, `quickSchema` в `shared/routes.ts`,
тесты `tests/quick-entry.test.ts`.

**Что осталось проверить на боевом сервере:** `client_max_body_size` у location `/api/` в nginx.
Комментарий в `client/src/lib/image.ts` утверждает, что прод режет тело на 1 МБ — фото из
шортката после ресайза до 1280 px в это укладывается, но если словишь 413 от nginx, поднимай
лимит до 2 МБ (в самом Express стоит `limit: "2mb"`).
