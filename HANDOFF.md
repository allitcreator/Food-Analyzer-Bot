## Цель

Починить фото-ветку быстрой записи: из шортката «Еда» → 📷 Сфотографировать
карточка КБЖУ в Telegram не приходит. Изначально жалоба была на фото БЕЗ
подписи, по ходу разбора выяснилось, что фото С подписью тоже не доезжает.

## Выполнено

1. **Найдена и починена причина отказа для фото без подписи.**
   Действие «Запросить ввод» в шорткате при пустом ответе всё равно кладёт в
   тело `text: ""`, а `quickSchema` требовала у `text` минимум один символ —
   запрос падал с `400 validation_error` ещё до бота. В `shared/routes.ts`
   пустой `text` теперь приводится к `undefined`; тело из одного пустого
   текста по-прежнему отвергается через `refine`. Регрессионный тест —
   `tests/quick-entry.test.ts`, кейсы «пустая строка» и «строка из пробелов».

2. **Проверено, что установленный шорткат не разошёлся с генератором.**
   `shortcuts/Еда.shortcut` расшифрован локально и разобран по действиям:
   AEA → сертификат подписи из auth-данных → `aea decrypt -sign-pub` →
   `aa extract` → `Shortcut.wflow` (bplist). Все 19 действий совпадают с
   тем, что собирает `scripts/build-shortcuts.py`.

3. **Проверена серверная фото-ветка.** `dispatchQuickEntry` (`sendPhoto` →
   `file_id` → `injectUserMessage`) и `buildSyntheticUpdate` на пустую и
   непустую подпись реагируют одинаково корректно — правка нужна была только
   в контракте.

4. **Собран диагностический шорткат** — `scripts/build-shortcuts.py`, функция
   `build_diag`, готовый подписанный файл `shortcuts/Еда (диагностика).shortcut`.
   Та же фото-ветка, но с двумя остановками: число символов base64 после
   сжатия и тело ответа сервера. Ссылки на переменные и состав действий
   проверены распаковкой уже подписанного файла.

5. **Симптом локализован по логам прода — гипотеза «размер тела» закрыта.**
   После деплоя `60a3dc0` пользователь снял два кадра, с подписью и без.
   Обе попытки видны в логах (10:42:39 и 10:43:02 MSK):

   ```
   POST /api/quick 400   тело ответа 199 байт, оба раза
   UA: BackgroundShortcutRunner/4711 CFNetwork/3860.700.1 Darwin/25.6.0
   ```

   Значит: шорткат работает и запрос доезжает до сервера целиком (иначе был
   бы `413`), размер тела ни при чём, а тело отвергает `quickSchema`. Оба
   кадра упали одинаково — ломается что-то общее, не пустая подпись.

6. **Причина отказа теперь пишется в лог** — `server/lib/quick-reject-log.ts`,
   вызов в `server/quick-api.ts`. Формат: `keys=[...] text=<len>
   imageBase64=<len> issues=[code@path]`. Содержимое полей не пишется
   (мегабайты base64 и подпись к еде как личные данные), это закреплено
   тестом.

7. **Причина отказа установлена: фото не доезжает вовсе.** Прогон после
   `ca4ef29`, два кадра (10:52:22 и 10:52:40 MSK):

   ```
   [quick] rejected: keys=[text,imageBase64] text=0 imageBase64=0 issues=[too_small@imageBase64]
   [quick] rejected: keys=[text,imageBase64] text=4 imageBase64=0 issues=[too_small@imageBase64]
   ```

   `imageBase64` приходит **пустой строкой**. Подпись при этом доезжает
   (`text=4`), значит сеть, токен, эндпоинт и текстовая ветка исправны.
   Ломается фото-ветка внутри шортката.

8. **Фото-ветка шортката починена (`643f03c`).** Две молчаливые причины,
   обе подтверждены документацией формата plist:

   - числа хранились сырыми (`WFImageResizeWidth: 1280`), а «Команды» держат
     числовые поля строками — нераспознанное значение становится `Auto`;
   - входы действий брались неявно от предыдущего. Такая цепочка рвётся без
     ошибки: Shortcuts подставляет пустоту и идёт дальше. Теперь `resize`,
     `convert` и `base64encode` получают вход явным `WFInput`
     (`WFTextTokenAttachment` со ссылкой на UUID конкретного действия).

   Сборка проверяет себя сама: `validate()` в `scripts/build-shortcuts.py`
   ловит битые ссылки на выходы, отсутствие явного входа и число не строкой.
   Проверено обратным тестом — если убрать `WFInput` у `base64encode`,
   сборка падает.

9. **Бот сам выдаёт шорткат (`643f03c`).** `/quick` отдаёт подписанный файл
   документом и объясняет установку: «Ненадёжные команды», подстановка
   токена, запуск. Файл едет из репозитория — собрать его на сервере нельзя,
   подпись ставит только macOS (`shortcuts sign -m anyone`), а токен в файл
   не зашивается, потому что подпись покрывает содержимое.

10. **Симптом сменился с 400 на 401 (`0a64489`).** Пользователь поставил
    новый шорткат из `/quick`, снял фото — в логах:

    ```
    11:25:12 POST /api/quick 401 in 5ms
    11:25:35 POST /api/quick 401 in 5ms
    ```

    До валидации тела дело не доходит: сервер не принимает токен. Значит
    новый шорткат установился и запросы шлёт, но заголовок `Authorization`
    не приведён в порядок. Фото-ветка при этом ещё ни разу не проверена —
    предыдущие два фикса остаются неподтверждёнными.

    Добавлена диагностика 401 по образцу 400: `describeAuthRejection`
    в `server/lib/quick-reject-log.ts`. В логе видна стадия — `no_header`,
    `placeholder=yes` (в заголовке остался текст-заглушка), `parsed=no`
    (лишнее слово или перенос в значении), `unknown_token`. Сам токен не
    логируется.

## Текущее состояние

Всё закоммичено, запушено и задеплоено. Прод на vps4 — `0a64489`, файлы
шорткатов лежат в контейнере (`/app/shortcuts`), бот поднялся.

Сервер в этом баге не был виноват: он получал пустое поле и корректно его
отвергал. Серверные гипотезы (лимит длины, `strict`) закрыты, фикс `90cd673`
симптом снять не мог.

Причина фикса не подтверждена прогоном: старый шорткат пользователь удалил,
сравнить «до и после» на телефоне уже нельзя. Оба дефекта реальны и оба
чинились вслепую по документации формата — если пустой `imageBase64`
повторится, значит есть третья причина, и её ищем по логу `[quick] rejected:`.

## Решения и ограничения

- Пустую подпись чиним на сервере, а не в шорткате: условие «не слать поле,
  если ввод пуст» в Shortcuts — лишняя ветка, которую человек сломает при
  первой правке. Пустая подпись — законный сценарий «просто фото».
- Диагностику собрали вместо подбора фикса вслепую: три возможные причины
  (валидация, размер тела, сбой уже после `202`) чинятся по-разному, а
  различает их одно число и один ответ сервера. По логам прода это в итоге
  решилось без телефона — остаётся только валидация.
- Причину отказа пишем на сервере, а не показываем в шорткате: тело 4xx
  клиенту всё равно не видно («Получить содержимое URL» ошибку проглатывает),
  а лог работает для всех пользователей и без пересборки шортката.
- Числовые параметры теперь пишутся строками (`"1280"`, `"0.7"`), а входы
  действий задаются явно. Оба решения приняты по документации формата, а не
  по подтверждённому эксперименту: телефон для сравнения «до и после» больше
  недоступен. Цена ошибки низкая — правки не ломают ничего, что работало.
- Целостность сборки проверяет `validate()`, а не ручная распаковка
  подписанного файла: ошибки такого рода на телефоне молчаливые, и ловить их
  надо до подписи.
- Токен в файл шортката не зашиваем. Подпись покрывает содержимое, так что
  файл с готовым токеном пришлось бы подписывать на каждого пользователя — на
  Linux-сервере это невозможно в принципе.
- Лимиты тела: nginx `location = /api/quick` — `client_max_body_size 2m`,
  express — `limit: "2mb"` (`server/index.ts:44`). Полный кадр с iPhone
  (3–5 МБ в base64) в них не влезает, ужатый 1280 px / 0.7 — влезает.

## Блокеры и риски

- **Блокер:** запросы с телефона отбиваются на 401 — токен в заголовке
  шортката не подставлен или испорчен. Пока это не починено, фото-ветка не
  проверяется в принципе.
- Фикс фото-ветки по-прежнему не подтверждён прогоном: до неё ни один запрос
  не дошёл. Обе правки сделаны по документации формата plist.
- Риск: если пустой `imageBase64` повторится, значит есть третья причина.
  Тогда нужен диагностический шорткат с остановкой после КАЖДОГО шага
  фото-ветки, а не только после base64.
- Файл шортката раздаётся из образа. Пересобрал шорткат — обязательно
  пересобрать и контейнер, иначе бот будет отдавать старую версию.
- Отложено с прошлой сессии: этап 2.3 релиза 2 (умные подсказки «топ-3 блюда
  по дню недели и времени») и два вопроса по Mini App и тумблеру
  `smart_reminders` — подробности в закрытом HANDOFF коммита `8adb699`.

## Следующий точный шаг

Сначала починить авторизацию — фото-ветку проверять бессмысленно, пока
запросы отбиваются на 401.

1. Открыть шорткат «Еда» → действие «Получить содержимое URL» → заголовок
   `Authorization`. Значение должно быть ровно `Bearer <48 hex-символов>`,
   одно слово `Bearer`, без переносов и пробелов по краям.
2. Токен взять из `/quick` (там же приходит файл шортката).
3. Запустить любую ветку и прочитать лог — он теперь называет стадию:

```
ssh vps4 'cd ~/foodbot && docker compose logs --since=15m bot | grep "\[quick\]"'
```

`placeholder=yes` — заголовок не тронут. `parsed=no` — значение испорчено,
чаще всего лишним словом `Bearer` при вставке целиком. `unknown_token` —
токен формально правильный, но серверу неизвестен: скорее всего был сброс
токена, нужно взять свежий из `/quick`.

После `202` прогнать все три пункта меню: 🎤 Сказать, ⌨️ Написать,
📷 Сфотографировать (последний дважды, с подписью и без). Каждая карточка
КБЖУ должна прийти в Telegram.

Если фото снова не доедет, причину смотреть там же:

```
ssh vps4 'cd ~/foodbot && docker compose logs --since=15m bot | grep "\[quick\]"'
```

`imageBase64=0` снова — значит есть третья причина потери картинки на
телефоне, и тогда нужен диагностический шорткат с остановкой после КАЖДОГО
шага фото-ветки, а не только после base64. Отсутствие строки `[quick]` при
непришедшей карточке — запрос вообще не ушёл, копать в шорткате.

После успешного прогона: удалить `shortcuts/Еда (диагностика).shortcut` и
`build_diag`, закрыть HANDOFF, вернуться к этапу 2.3.
