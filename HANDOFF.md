## Цель

Починить фото-ветку быстрой записи: из шортката «Еда» → 📷 Сфотографировать
карточка КБЖУ в Telegram не приходит. Изначально жалоба была на фото БЕЗ

## Выполнено

1. **Найдена и починена причина отказа для фото без подписи.**
   Действие «Запросить ввод» в шорткате при пустом ответе всё равно кладёт в
   тело `text: ""`, а `quickSchema` требовала у `text` минимум один символ —
   запрос падал с `400 validation_error` ещё до бота. В `shared/routes.ts`
   пустой `text` теперь приводится к `undefined`; тело из одного пустого
   текста по-прежнему отвергается через `refine`. Регрессионный тест —
   `tests/quick-entry.test.ts`, кейсы «пустая строка» и «строка из пробелов».

   `shortcuts/Еда.shortcut` расшифрован локально и разобран по действиям:
   AEA → сертификат подписи из auth-данных → `aea decrypt -sign-pub` →
   `aa extract` → `Shortcut.wflow` (bplist). Все 19 действий совпадают с
   тем, что собирает `scripts/build-shortcuts.py`.

8. **Фото-ветка шортката починена (`643f03c`).** Две молчаливые причины,
   обе подтверждены документацией формата plist:

     числовые поля строками — нераспознанное значение становится `Auto`;

     ошибки: Shortcuts подставляет пустоту и идёт дальше. Теперь `resize`,
     `convert` и `base64encode` получают вход явным `WFInput`

   Сборка проверяет себя сама: `validate()` в `scripts/build-shortcuts.py`
   ловит битые ссылки на выходы, отсутствие явного входа и число не строкой.
   Проверено обратным тестом — если убрать `WFInput` у `base64encode`,
   сборка падает.

14. **Первый замер: все три числа нулевые.** Пользователь прогнал

    Диагностика переписана под прямое сравнение: один снимок кодируется

16. **Фото переведено на бинарную отправку (`dd93e22`).** Косвенное
    рассуждение: в шорткате работает всё короткое (токен, подпись, текстовая
    ветка) и не работает единственная строка на 300+ КБ. Поэтому base64 из
    фото-ветки убран совсем — снимок уходит телом запроса как файл

    «Получить содержимое URL».

    Подпись переехала в query с URL-кодированием (`is.workflow.actions.urlencode`):
    тело занято файлом. Сервер принимает оба формата, контракт общий —
    `bodyFromBinary` приводит бинарь к тому же объекту и отдаёт в `quickSchema`.
    В логе отказа видно путь и число байт (`binary=<N>`).

    Из `take_photo` убран необязательный `WFCameraCaptureShowPreview`: сырое
    булево — тот же класс риска, что и сырые числа.

17. **Первый прогон бинарной отправки: тело не распарсилось (`d711f96`).**

    ```

    ```

    тела. Важное: сам запрос дошёл и авторизацию прошёл — то есть фото-ветка

    Правило переписано от противного: JSON забирает `express.json`, всё
    остальное читается как байты (`isBinaryContentType`). `Content-Type`
    добавлен в лог отказа.

шорткатов лежат в контейнере (`/app/shortcuts`), бот поднялся.

## Решения и ограничения

- Пустую подпись чиним на сервере, а не в шорткате: условие «не слать поле,
  если ввод пуст» в Shortcuts — лишняя ветка, которую человек сломает при
  первой правке. Пустая подпись — законный сценарий «просто фото».
- Диагностику собрали вместо подбора фикса вслепую: три возможные причины
  (валидация, размер тела, сбой уже после `202`) чинятся по-разному, а
  различает их одно число и один ответ сервера. По логам прода это в итоге
  решилось без телефона — остаётся только валидация.
- Причину отказа пишем на сервере, а не показываем в шорткате: тело 4xx
  клиенту всё равно не видно («Получить содержимое URL» ошибку проглатывает),
  а лог работает для всех пользователей и без пересборки шортката.
- Числовые параметры теперь пишутся строками (`"1280"`, `"0.7"`), а входы
  действий задаются явно. Оба решения приняты по документации формата, а не
  по подтверждённому эксперименту: телефон для сравнения «до и после» больше
  недоступен. Цена ошибки низкая — правки не ломают ничего, что работало.
- Целостность сборки проверяет `validate()`, а не ручная распаковка
  подписанного файла: ошибки такого рода на телефоне молчаливые, и ловить их
  надо до подписи.
- Токен в файл шортката не зашиваем. Подпись покрывает содержимое, так что
  файл с готовым токеном пришлось бы подписывать на каждого пользователя — на
  Linux-сервере это невозможно в принципе.
- Сжатие на телефоне убрано временно и осознанно: три кандидата на потерю
  снимка проверяются разом, а не по очереди. Возвращать по одному действию,
  когда путь заработает, — иначе снова непонятно, что именно сломало.
- Лимит `8m` — плата за полный кадр, а не желаемое состояние. Отсечка в nginx
  срабатывает ДО проверки токена, то есть защищает и от неавторизованных
  запросов; чем она выше, тем больше сервер готов принять от кого угодно.
  Цена одного запроса сейчас — около 13 МБ памяти на пике (буфер 4 МБ +
  base64-строка 5 МБ + обратный буфер 4 МБ). На vps4 это некритично (2 ГБ
  памяти, ~1 ГБ свободно, бот ест 80 МБ, есть rate limit 30/час), но
  держать запас без нужды незачем.
- Сервер принимает оба формата тела (JSON и бинарь) и приводит их к общему
  контракту. Раздваивать `quickSchema` не стали: правила про размер, пустоту
  и подпись должны остаться едиными.
- Лимиты тела: nginx `location = /api/quick` — `client_max_body_size 2m`,
  express — `limit: "2mb"` (`server/index.ts:44`). Полный кадр с iPhone
  (3–5 МБ в base64) в них не влезает, ужатый 1280 px / 0.7 — влезает.

## Блокеры и риски

- Блокеров нет. Осталось подтвердить сквозной сценарий: кадр должен дойти
  до Telegram и вернуться карточкой КБЖУ.
- Открытый вопрос: снимок едет полным кадром 3–5 МБ. Сжатие возвращать по
  одному действию (`resize`, затем `convert`), проверяя каждое — одно из них
  и было причиной потери.
- После возврата сжатия опустить `client_max_body_size` обратно (ориентир
  `3m`) и `express.raw` соразмерно.
- Отдельная оптимизация: бинарный путь гоняет байты через base64 и обратно
  только ради общей схемы. Передавать буфер прямо в `sendPhoto` — пик памяти
  на запрос упадёт примерно втрое.
- Опасение про HEIC снято: телефон прислал `image/jpeg`, Telegram такой
  формат принимает.
- Бинарная отправка сама по себе исправна: запрос доходит и проходит
  авторизацию, пустое тело — следствие пустого снимка, а не транспорта.
- `WFHTTPBodyType: File` частично подтверждён на устройстве: запрос дошёл до
  сервера и прошёл авторизацию, чего с base64 не случалось ни разу. Не
  подтверждено пока одно — что в теле едет именно картинка и она непустая.
- Запасной путь, если и бинарь не доедет: фото прямо в чат боту (работает
  сейчас, разработки не требует), фото-ветку из шортката тогда убрать.
- `client_max_body_size` в nginx остался `2m`: правка конфига заблокирована
  политикой. Сжатый кадр (150–400 КБ) влезает, но если сжатие на телефоне не
  отработает, будет `413`. Поднять: `sudo sed -i 's/client_max_body_size 2m;/client_max_body_size 8m;/' /etc/nginx/sites-available/bots && sudo nginx -t && sudo systemctl reload nginx`
- Известно точно: текстовая и голосовая ветки работают, авторизация работает,
  сервер исправен. Ломается только цепочка съёмка → base64.
- Риск: если пустой `imageBase64` повторится, значит есть третья причина.
  Тогда нужен диагностический шорткат с остановкой после КАЖДОГО шага
  фото-ветки, а не только после base64.
- Файл шортката раздаётся из образа. Пересобрал шорткат — обязательно
  пересобрать и контейнер, иначе бот будет отдавать старую версию.
- Отложено с прошлой сессии: этап 2.3 релиза 2 (умные подсказки «топ-3 блюда
  по дню недели и времени») и два вопроса по Mini App и тумблеру
  `smart_reminders` — подробности в закрытом HANDOFF коммита `8adb699`.

Старый диагностический материал, если понадобится:

```
ssh vps4 'cd ~/foodbot && docker compose logs --since=15m bot | grep "\[quick\]"'
```

- `202` и карточка КБЖУ в чате — готово, задача закрыта;
- `binary=<N>` с ненулевым N и `400` — файл дошёл, ошибка в схеме, чинить
  сервер; в строке лога рядом виден `ct=` — фактический Content-Type;
- `binary=0` — снимок не доехал и в бинарном режиме, значит теряется сам
  кадр; тогда переходить на запасной путь (фото прямо в чат боту) и убирать
  фото-ветку из шортката;
- `413` в nginx-логе — сжатие не отработало, поднять `client_max_body_size`.

Для справки, лог сервера называет стадию отказа:

```
ssh vps4 'cd ~/foodbot && docker compose logs --since=15m bot | grep "\[quick\]"'
```

`placeholder=yes` — заголовок не тронут. `parsed=no` — значение испорчено,
чаще всего лишним словом `Bearer` при вставке целиком. `unknown_token` —
токен формально правильный, но серверу неизвестен: скорее всего был сброс
токена, нужно взять свежий из `/quick`.

После `202` прогнать все три пункта меню: 🎤 Сказать, ⌨️ Написать,

## Rollback

Правка nginx живёт вне git и откатывается отдельно:

```
sudo sed -i '64s/client_max_body_size 8m;/client_max_body_size 2m;/' /etc/nginx/sites-available/bots && sudo nginx -t && sudo systemctl reload nginx
```

Код:

```
git revert f0b74c3 00b4fcd d711f96 dd93e22 cf502a4 306eaba caba8a8 520395a 0a64489 643f03c ca4ef29 60a3dc0 90cd673
```

Затем на vps4: `cd ~/foodbot && git pull origin main && docker compose up -d --build`.

Схема БД не тронута, миграций с этими коммитами не было. Единственное
изменение вне репозитория — `client_max_body_size` в nginx, оно откатывается
командой выше.
